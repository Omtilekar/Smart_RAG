# Phase 2 Independent Benchmark Validation (FinanceBench)

Established in Task 2.12. Validates the project's evaluation and RAG
retrieval machinery against FinanceBench, an independently authored
financial QA benchmark, without changing the benchmark to fit the
system and without tuning the system to the benchmark.

## Objective

FinanceBench answers a question the internal Task 2.3 evaluation set
cannot: the internal set's questions and expected answers were both
generated by the same templated logic, so a systematic flaw in that
generator would inflate every internal score invisibly. FinanceBench's
150 questions were authored and annotated by people outside this
project, over real 10-K/10-Q/8-K/earnings filings this project did not
select. Agreement or divergence between the two is external evidence
about whether the evaluation system itself is trustworthy - it is never
a tuning target for Phase 3.

## Relationship to `PROJECT_EXECUTION.md`

`PROJECT_EXECUTION.md`'s Task 2.12 checklist is materially narrower and
more concrete than this task's own drafting prompt, and **wins** per
this task's own Section 3 rule. Two documented resolutions:

1. **Scope is retrieval-only, not generation.** `PROJECT_EXECUTION.md`'s
   checklist ("Run the same retrieval harness against it," "Report
   FinanceBench metrics alongside the internal set") never mentions
   answer generation or LLM calls. Combined with the drafting prompt's
   own Section 26 ("do not assume Task 2.12 must call an LLM unless the
   authoritative local contract requires it... If retrieval/evidence
   validation only: LLM calls=0, API spend=$0"), this task performs
   **zero** generation and **zero** LLM calls. Semantic answer accuracy
   is explicitly deferred to Task 2.13.
2. **Isolated corpus, not merged into the SEC development corpus.**
   `PROJECT_EXECUTION.md` says "Add the referenced filings to the
   development corpus where they are not already present," which could
   be read as merging FinanceBench's PDFs into Phase 1's SEC corpus.
   Interpreted instead as "acquire the referenced source documents
   locally" - built into an isolated `data/financebench/` +
   `artifacts/benchmark/financebench/<hash>/` namespace, never touching
   `data/edgar_corpus/`, Phase 1's `artifacts/chunks/<hash>/`, Phase 1's
   embeddings, or the Phase 1 LanceDB table. This reading is required by
   the drafting prompt's own hard leakage/isolation rules (Sections 8,
   13, 21) and by the general project principle of never mutating a
   frozen historical baseline (Sections 57, 59-60) - not a scope
   override, a documented interpretation of an ambiguous instruction.

## Page-number convention

FinanceBench's `evidence_page_num` is **zero-indexed**, matching a
Python-list-style page position (`pdfplumber`'s `pdf.pages[n]`), **not**
the PDF's printed/display page number. Confirmed empirically: on
`3M_2018_10K`, `evidence_page_num=59` locates the page containing the
target cash-flow-statement text at `pdf.pages[59]` (the PDF's own
59th/60th printed page, off by one from the zero-indexed value). Every
internal page reference in this task's artifacts uses this same
zero-indexed convention (`PAGE_NUMBER_CONVENTION = "zero_indexed_pdf_page_list_position"`),
never mixed with a 1-indexed display page.

## No-leakage contract

The retrieval corpus is built exclusively from each `doc_name`'s
official source PDF, parsed independently page-by-page. `evidence_text`,
`justification`, `answer`, and `question` are never indexed -
`src.eval.financebench.assert_no_gold_leakage()` raises `LeakageError`
outright if a caller ever declares one of those fields as a retrieval-
corpus source. The headline retrieval run searches the **complete**
84-document benchmark corpus for every question - never a gold-document
prefilter (Section 22).

## PDF parsing

Docling's PDF pipeline (`docling.document_converter.DocumentConverter`
against a real FinanceBench PDF) requires a layout ML model
(`docling-project/docling-layout-heron`) that itself requires
`torchvision`, which this repository deliberately excludes (Task 2.8's
own hard-won lesson: installing torchvision extras previously broke the
pinned CUDA `torch`/`transformers`/`sentence-transformers` stack).
Verified directly - the PDF pipeline fails immediately with
`RuntimeError: ... AutoImageProcessor requires the Torchvision library`.
Rather than reinstalling torchvision and risking that same regression,
this task adds `pdfplumber` (pure Python + `pdfminer.six`, MIT license,
zero torch/torchvision dependency - verified `pip check` clean after
installation) as the PDF text/table extraction backend. `docling-slim`
remains the HTML/inline-XBRL backend for Task 2.8; it is never forced
onto PDFs.

## Table handling

`page.extract_tables()` output is preserved per page (row/column
structure, cell text) in the parsed artifact alongside `page.extract_text()`.
One predetermined serialization (`serialize_table()`: pipe-delimited
cells per row, rows newline-joined, a missing cell as an empty string)
was frozen before seeing any benchmark result - never changed because it
scored better. The retrieval/embedding/chunking pipeline itself indexes
`page.extract_text()` (the same text FinanceBench's own evidence
excerpts are drawn from), not the separately-serialized table
representation - this is a deliberate choice to keep the alignment path
consistent with what FinanceBench's evidence was extracted against.

## Evidence alignment

`src.eval.financebench.align_evidence_item()`: checks the evidence's
stated page first (raw substring, then whitespace-normalized substring);
if absent there, checks the two immediately adjacent pages (a common
off-by-one from a different extraction tool's pagination). More than one
distinct matching page -> `ambiguous`. No match anywhere checked ->
`unmatched`. Never uses an LLM (Task 2.13 owns semantic judgment); never
fabricates a confidence score.

**Normalization is whitespace collapse plus one narrow, empirically-
justified extra rule**: dash-family and bullet-family marker glyphs
(em/en dash, minus sign, `•`/`‣`/`◦`/`▪`) are treated as whitespace
before collapsing. Two concrete real-document cases forced this, both
found and fixed during this task's own required pilot (Section 35 -
"only fix correctness defects," never tune based on pilot scores):

1. `3M_2018_10K` page 59: FinanceBench's evidence_text reads "...Other
   net..." where the real page (via `pdfplumber`) reads "...Other —
   net..." - a blank/zero-value table-cell placeholder dash rendered
   only by one of the two extraction tools.
2. `AMD_2022_10K` page 3: a bulleted list item - `pdfplumber` preserves
   the literal `•` glyph, FinanceBench's own evidence_text extraction
   drops it entirely.

Both are extraction-tool-dependent marker glyphs, never semantic
content - normal ASCII hyphens (e.g. "non-GAAP") are never touched.
This is not a general fuzzy-match escape hatch - no other character
class is altered, and only `exact`/`normalized_exact` alignments ever
become retrieval gold (`ambiguous`/`unmatched` remain diagnostic,
per Section 17).

**Gold chunk attribution**: once a page is aligned, `gold_chunk_ids_for_alignment()`
identifies which specific chunk(s) on that page contain the evidence
text (exact, then normalized-exact); if the evidence spans a chunk
boundary and no single chunk contains it whole, every chunk on that page
is conservatively attributed as gold rather than guessing which one.

## Benchmark chunking

Frozen before seeing any result (Section 18): the same BAAI/bge-small-en-v1.5
tokenizer, 512-content-token windows, zero overlap, final partial window
kept - identical to Phase 1's own baseline semantics
(`src.chunk.fixed_window.compute_token_windows()`, reused directly, not
reimplemented) - with exactly one benchmark-specific deviation: a window
never crosses a page boundary, since FinanceBench evidence identity is
page-oriented and crossing pages would make gold-chunk mapping
ambiguous. This page-bounded constraint is explicitly a benchmark-
specific accommodation, not a new production chunking recommendation.

Chunk IDs (`financebench:<doc_name>:page<NNNNN>:chunk<NNNN>`) are
namespaced so they can never collide with Phase 1's SEC chunk IDs
(`{document_id}::chunk{ordinal}`) or Task 2.9's `chunk_uid` - FinanceBench
never mutates the internal SEC chunk schema.

## Retrieval metrics

Document-level and evidence/chunk-level recall@10 and MRR, computed by
`src.eval.financebench.evaluate_financebench_question()`/
`aggregate_financebench_results()` - the same rank-based mathematics as
Task 2.6's SEC metrics, independently re-implemented and unit-tested
against FinanceBench's own `doc_name`/chunk-id identifiers (Section 23:
adapt only the identifier abstraction, not the mathematical definition).
`evidence_recall@10` is the **mean of each question's own**
`hits_in_top_k / len(gold_chunks)` fraction (macro-average across
questions with at least one aligned gold item) - the same shape Task
2.7's MS MARCO `passage_recall_at_k` uses, not a pooled/micro-averaged
ratio.

Evidence coverage is reported **before** evidence metrics (Section 24):
a question contributes to `evidence_recall@10`/`evidence_mrr` only if at
least one of its evidence items aligned `exact`/`normalized_exact`; a
question with zero aligned evidence is `blocked_evidence_unmatched` and
excluded from both the evidence-metric numerator/denominator and the
`doc_recall@10` denominator alike (see Real Results below for exact
counts) - never silently dropped without a status.

## Run logging - external-benchmark extension

`src/eval/run_logging.py`'s `split` field was originally validated
against Task 2.5's `VALID_SPLITS = ("dev", "test", "ci")` only -
FinanceBench cannot honestly be represented that way (it is not the
protected internal SEC `test` split, and forcing it into that value
would be a direct lie). Rather than shoehorning FinanceBench into
internal split semantics, `EVALUATION_RUN_SCHEMA_VERSION` was bumped
`1 -> 2` to add:

```text
evaluation_source:      "internal_phase2" (default) | "external_benchmark"
benchmark_name:          null for internal runs; required for external runs
benchmark_version:       null for internal runs; required for external runs
benchmark_source_hash:   null for internal runs; required (SHA-256) for external runs
```

For `evaluation_source="internal_phase2"` (the only value Task 2.11 ever
used), behavior is byte-for-byte unchanged - `split` must still be one
of `VALID_SPLITS`. For `evaluation_source="external_benchmark"`, `split`
is the benchmark's own free-form population label (`"open_source_150"`
here) - never coerced into `dev`/`test`/`ci`. `SUPPORTED_RUN_SCHEMA_VERSIONS
= (1, 2)`: a genuine `run_schema_version=1` record (predating these four
fields entirely) still validates and loads correctly -
`_backfill_v1_defaults()` supplies the v1-implicit
`evaluation_source="internal_phase2"` when constructing the in-memory
record. `src.eval.evaluation_schema.VALID_SPLITS` itself was never
modified. No pre-existing v1 record needed migration - `results/eval_runs/`
was still empty at the start of this task.

The real full-benchmark run's Task 2.11 record is at
`results/eval_runs/<run_id>.json` (see Real Results below for the exact
`run_id`) - `evaluation_source="external_benchmark"`,
`benchmark_name="financebench"`.

**Interpretation**: document-level retrieval is strong (92.2% recall@10
across the full 84-document benchmark corpus, no gold-document
prefilter) - the frozen Phase 1 baseline retriever finds the right
source document for the overwhelming majority of FinanceBench questions
even outside its native SEC-corpus domain. Evidence/chunk-level recall
is measured only over the 77 questions (51%) whose gold evidence
aligned `exact`/`normalized_exact` to a specific page; the remaining 73
(49%) are honestly excluded as `blocked_evidence_unmatched`, not
silently scored as failures or folded into a misleadingly larger
denominator. Manually inspecting several `unmatched` cases (see
"Evidence alignment" above) found the cause is real multi-column
financial-table reading-order divergence between FinanceBench's own
extraction tool and `pdfplumber`, not a code defect - two genuine
narrower bugs (dash and bullet marker glyphs) were found and fixed
during the pilot and are reflected in this 77/150 figure.

No large gap-investigation against the internal Task 2.3 set was
triggered by a suspicious divergence in the *comparable* metric
(document-level retrieval): Task 1.10's internal Phase 1 smoke baseline
measured `doc_recall@10 = 0.970000` on its own 200-question SEC-only
smoke set, and FinanceBench's `doc_recall@10 = 0.9221` on a materially
different, harder, cross-company financial-PDF corpus is a comparable
order of magnitude, not a wide divergence suggesting internal-generator
bias.

## Known limitations

- `evidence_recall@10`/`evidence_mrr` are computed only over questions
  with at least one `exact`/`normalized_exact`-aligned evidence item;
  the exact coverage denominator is in the result summary, never
  silently assumed to be 150/150.
- Table-heavy, multi-column financial tables where FinanceBench's own
  evidence-extraction tool and `pdfplumber` diverge on **column/row
  reading order** (not merely a marker-glyph difference) remain
  genuinely `unmatched` - this is an honest, expected limitation of
  linear PDF text extraction on complex tables, not a code defect, and
  was not "fixed" by loosening the alignment criteria (which would cross
  into an undefensible fuzzy match).
- No OCR was used or required - all 84 referenced PDFs have an
  extractable native text layer.
- Semantic answer-accuracy is entirely deferred to Task 2.13.
